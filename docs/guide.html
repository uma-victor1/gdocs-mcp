gdocs

Google Docs review loop

Claude Code reads your Google Doc and its comment threads, then writes corrections back into the same Doc at the same URL. No pasting the draft into Docs. No pasting reviewer feedback back into the terminal.

The point

What it removes

Markdown in your repo stays the source of truth. The Doc is only a review surface. Everything between those two facts used to be manual.

Before

  1. Copy Markdown out of the editor
  2. Paste into a new Google Doc
  3. Reviewers comment
  4. Read each comment, retype it into the terminal
  5. Fix, then re-paste the whole draft into a fresh Doc
  6. Old comment threads are stranded on the old Doc

After

  1. Ask Claude to read the Doc
  2. Comments arrive with the exact sentence each one is anchored to
  3. Fix the Markdown in your repo
  4. Push back into the same Doc, same URL
  5. Reply to reviewers in their own threads
Before you
start

Requirements

  • Node 18 or newer
  • The claude CLI
  • A Google account, plus roughly ten minutes in Google Cloud Console

Setup is a strict sequence — each step depends on the one before it — so the five steps below are numbered rather than listed.

Setup

1install

Run the installer

From the server's directory. It installs dependencies, verifies the server actually starts, and registers it with Claude Code at user scope so it is available in every project.

./install.sh
2google
cloud

Create a project and enable two APIs

Create a project at console.cloud.google.com, then under APIs & Services › Library enable both:

  • Google Docs API — reading and editing document bodies
  • Google Drive API — comment threads, Markdown export, in-place upload
3consent

Configure the OAuth consent screen

User type External is correct for a personal Google account. Under Audience, add as a test user the exact address you will sign in with.

Skip this and step 5 fails

You get Error 403: access_denied and “has not completed the Google verification process”. It is not asking you to get the app verified — it is saying that address is not on the tester list. Add it, save, retry.

Watch which account you use. If you are signed into several Google accounts, the one the browser picks must be the one on the list.

4credentials

Download the OAuth client and put it in place

Go to Credentials › Create credentials › OAuth client ID, choose Desktop app, and download the JSON. Save it as:

~/.config/gdocs-mcp/credentials.json

Credentials live outside any repository deliberately, so git add -A can never commit them.

5authorise

Grant access, once

npm run auth

Your browser opens. Google warns that the app is unverified, which is expected for a one-user app: choose Advanced › Go to … (unsafe). The refresh token is written to ~/.config/gdocs-mcp/token.json with permissions 0600.

Restart Claude Code, then confirm:

claude mcp list
Expect this

You will re-authorise weekly

While the consent screen sits in Testing, Google expires the refresh token every seven days. That is documented behaviour for external apps in testing, not a fault in the server.

There is no way around it for this scope set. auth/drive is a restricted scope, and publishing to production with a restricted scope requires a CASA security assessment by a Google-empanelled assessor — disproportionate for a one-person tool.

So about once a week a call fails with “Authorisation expired”. The fix takes fifteen seconds:

npm run auth

Unless you have Google Workspace

If you have a Workspace account, you can avoid this entirely: create the Cloud project under that organisation and set the consent screen user type to Internal. Internal apps have no seven-day expiry and no tester list at all.

Reference

The nine tools

Every tool accepts either a Google Doc URL or a bare file ID.

ToolWhat it does
find_docSearch Drive for Docs by title
read_docDocument body as Markdown, plus every comment thread with the text it is anchored to
read_commentsComment threads only — the cheap “any new feedback?” check
replace_textExact find-and-replace, in placekeeps anchors
append_textAdd a paragraph at the end, with heading level, point size, colour, bold or italickeeps anchors

reply_commentPost a reply inside a reviewer's thread
resolve_commentResolve a thread with a closing note
create_docNew Doc from a Markdown file — once per document

The comment-anchor tradeoff

Why this matters more than it sounds

Google anchors every comment to a specific span of text. Rewrite that span and the thread detaches or auto-resolves — the reviewer's context is gone, and nobody gets told.

So the loop has a shape:

  • Small fixes use replace_text. Anchors survive and reviewers keep their context.
  • Adding rather than changing uses append_text. It only ever inserts at the end, so no existing span moves and nothing can detach.
  • Structural rewrites use push_markdown. Faster, but expect thread loss. It reports how many open threads existed beforehand, so the damage is visible rather than silent.
  • Reply before you rewrite. A reply leaves a record of what changed and why, which is what a reviewer actually wanted from the thread.
In practice

What you type

Plain requests. Claude picks the tools.

> any new comments on the draft doc?

> pull the comments, fix draft.md for each one,
  then reply on each thread saying what changed

> push the updated draft.md back to the doc

Because the repo file is the source of truth, the useful habit is to fix the Markdown first and push second. The Doc is downstream of your editor, never the other way round.

Trust

Why a hand-built server

An MCP server holding a Google Docs OAuth token can read and rewrite every document in the account, and it runs as local code on your machine.

There is no first-party Google or Anthropic Docs MCP. Every published one is a third-party package from an individual publisher. This server is roughly 250 lines built on Anthropic's MCP SDK and Google's own client library — small enough to read in full before you trust it with that token.

Turning writes off

Reads keep working, every write tool refuses:

claude mcp remove gdocs -s user
claude mcp add gdocs -s user \
  -e GDOCS_MCP_READONLY=1 \
  -- node "$PWD/server.mjs"

Useful when the Doc belongs to somebody else.

Revoking access

Revoke at myaccount.google.com/permissions, then delete ~/.config/gdocs-mcp/token.json.

You can always check the server independently of Claude Code with npm run smoke, which starts it and lists its tools.
